# Tauri + React Desktop Integration

## Goal

Replace the deleted MAUI wallet shell with a desktop application built from:

1. `Tauri` for the native shell
2. `React + Vite` for the renderer UI
3. a local `.NET` backend process for wallet logic, storage, signing, ESR handling, and blockchain access

This is a desktop app, not a browser-first web app.

## Why This Direction

The removed MAUI shell created too much friction for desktop layout quality and long-term frontend velocity. The repository already contains reusable .NET blockchain and ESR libraries, so the correct split is:

- UI in React
- security-critical wallet logic in .NET

That preserves local custody, keeps signing out of JavaScript, and gives the UI layer a mature desktop-web layout system.

## Process Model

### 1. Tauri Shell
- creates native windows
- handles desktop packaging and auto-update later if needed
- registers custom protocols like `esr://` and `anchor://`
- starts and stops the local .NET backend process

### 2. React Renderer
- dashboard, send flow, approvals, settings, account management
- no private key storage
- no direct signing logic
- communicates only with the local backend

### 3. Local .NET Backend
- owns wallet storage and encryption
- owns ESR parsing and session handling
- owns transaction construction, signing, and broadcast
- exposes a local API to the bundled desktop shell

## Security Boundary

The React renderer must be treated as an untrusted presentation layer.

### Keep in .NET
- private key storage
- password verification
- mnemonic handling
- signing
- transaction broadcast
- ESR callback/session state

### Keep out of React
- raw private keys
- decrypted key material
- direct signing implementations

## Local Communication Options

### Option A: localhost HTTP API
Best for simplicity and fast iteration.

Pros:
- easy to debug
- easy to version
- frontend tooling works naturally

Cons:
- must secure local access carefully

### Option B: named pipes / Tauri commands
Best for tighter local-only transport.

Pros:
- smaller attack surface than HTTP
- no port management

Cons:
- more integration work
- less convenient during frontend iteration

### Recommended Start
Use localhost HTTP with a short-lived session token generated by the shell on startup, then tighten transport later if needed.

## Startup Sequence

1. User launches desktop app.
2. Tauri starts the local .NET backend.
3. Backend binds to localhost and emits a startup token.
4. Tauri injects the token into the renderer startup environment.
5. React connects to the backend and loads app state.

## ESR / Protocol Flow

1. OS dispatches `esr://` or `anchor://` to the desktop shell.
2. Tauri receives the protocol activation.
3. Tauri forwards the raw URI to the local .NET backend.
4. Backend parses the ESR via `SUS.EOS.EosioSigningRequest`.
5. React displays the approval UI using parsed request data.
6. User approves or rejects.
7. Backend signs, optionally broadcasts, and returns callback data.
8. Backend sends the callback or session response.

## Signing Flow

1. Renderer sends a sign request ID or transaction payload reference.
2. Backend validates session and wallet state.
3. Backend requests unlock or password confirmation if needed.
4. Backend signs using `SUS.EOS.Sharp`.
5. Backend returns a signed result or broadcast result.

The renderer should never receive decrypted secrets.

## Backend Responsibilities

The backend executable should be thin and orchestration-oriented.

Use the existing libraries for:
- chain RPC access
- asset parsing
- transaction serialization
- cryptographic signing
- ESR request handling

Avoid burying frontend-specific assumptions into the shared libraries.

## Frontend Responsibilities

React should handle:
- layout and navigation
- lists, forms, popovers, approval modals
- local optimistic UI state
- request polling or subscriptions to the backend

React should not handle:
- secure storage
- cryptography
- blockchain signing primitives

## Packaging Notes

### Windows
- Tauri bundles the desktop shell
- .NET backend ships as a sibling executable
- protocol registration is handled by the installer or Tauri config

### macOS / Linux
- same general split applies
- backend lifecycle and bundling rules differ per platform

## Migration Phases

### Phase 1
- keep and stabilize `SUS.EOS.Sharp`
- keep and stabilize `SUS.EOS.EosioSigningRequest`
- define the local backend API

### Phase 2
- create backend executable wrapping the reusable libraries
- implement unlock, accounts, balances, sign, and ESR endpoints

### Phase 3
- create Tauri + React shell
- recreate dashboard and ESR approval flow

### Phase 4
- package protocol handling and release pipeline

## What This Repository No Longer Contains

- MAUI pages
- MAUI platform heads
- MAUI navigation, styles, or app-shell logic

Those concerns were intentionally removed rather than migrated.
